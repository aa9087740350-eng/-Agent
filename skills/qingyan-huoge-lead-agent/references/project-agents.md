# AGENTS.md

## 项目定位

本项目是“清研霍格精工拓客智能体”，目标不是采集高校教授名单，而是识别近期可能存在科研样件、实验装置、夹具、结构件、小批量试制、设计优化需求的潜在客户，并帮助客户经理判断：

1. 今天最该联系谁
2. 为什么现在联系
3. 应该找谁、怎么开口

所有 AI 生成结果必须可追溯、可解释、可人工复核。MVP 阶段不得自动发送邮件、微信、短信或电话，所有触达动作必须由客户经理人工确认。

修改项目逻辑前，必须优先阅读根目录 `README.md`，并确认改动属于哪一层。

## 分层边界

系统按以下层次拆分，AI 不得跨层混写逻辑：

1. 目标区域与客户画像层
   只负责区域、区域权重、目标高校/机构、客户类型、优先学科、排除规则。

2. 公开线索采集层
   只负责从高校官网、学院新闻、课题组主页、导师主页、论文摘要、专利摘要、采购公告、招聘、成果转化新闻、科技园企业名单、公众号文章等公开来源采集信息。
   必须保留来源 URL、采集日期、标题、证据片段。

3. 需求信号识别层
   只负责识别研究方向、显性需求信号、痛点信号、近期紧迫信号、切入点、假阳性风险。
   不得直接决定最终客户优先级。

4. 动态评分层
   只负责基于已识别信号、区域、机构类型、学科方向、近期性、触达可行性和历史反馈打分。
   必须输出评分理由，不得修改原始证据。

5. 联系人识别层
   只负责按回应概率推荐联系人，例如博士/硕士作者、实验室工程师、博后/项目助理、PI、科研秘书。
   必须说明推荐原因。

6. 客户卡片与话术生成层
   只负责生成客户卡片、邮件、微信、电话开场建议。
   不得执行真实触达。

7. 销售反馈与模型优化层
   负责记录客户经理反馈，并用于后续优化评分权重、标签规则和假阳性识别。

## 开发规则

### 应做

- 修改前先判断变更属于哪个层级。
- 新增字段时优先兼容 `README.md` 中定义的客户卡片和 Excel 输出字段。
- 每条线索至少包含：线索 ID、采集日期、学校/机构、学院/实验室、负责人或团队、需求信号、证据片段、来源 URL、评分、评分理由。
- 所有评分必须可解释，不能只返回分数。
- 联系人推荐必须说明回应概率依据。
- 所有涉及信号识别、评分、联系人推荐、话术生成的 Prompt 模板，必须作为代码资产纳入版本管理，建议放在 `/prompts`。
- 修改评分规则、核心识别 Prompt、联系人推荐 Prompt 或话术 Prompt 后，必须跑固定回归测试样例集，覆盖高潜和低潜样本。

### 禁做

- 不得删除来源 URL、采集日期、证据片段、评分理由等可追溯字段。
- 不得把采集、识别、评分、联系人推荐、话术生成混成一个不可追踪的大步骤。
- 不得让采集层直接给客户最终评级。
- 不得让评分层反向篡改原始采集证据。
- 不得只输出教授名单、邮箱列表或机构名单。
- 不得硬编码单一学校、地区或客户类型，除非该逻辑明确属于 MVP 配置。
- 不得在线上临时修改 Prompt 后不留 Git 记录。
- 不得在未跑回归样例的情况下调整核心评分或识别规则。

## AI 置信度兜底规则

### 应做

- 当 AI 无法从公开来源确认具体联系人、邮箱、电话或微信号时，必须标记为 `未识别`、`未公开` 或 `待人工确认`。
- 当线索的 `显性需求信号` 和 `痛点信号` 均为空时，即使区域、机构类型、学科方向高度匹配，最终评级也必须强制锁定为 `C` 或 `D`。
- 所有 `A+`、`A` 级线索必须至少包含一个可追溯的近期需求信号或痛点信号。
- 对证据不足但方向相关的客户，应进入观察池，而不是高优先级触达池。

### 禁做

- 不得通过姓名拼音、学校域名、学院域名、常见邮箱格式或通用域名猜测邮箱。
- 不得为了补齐客户卡片而虚构联系人身份、职务、联系方式或回应概率。
- 不得为了凑齐每日客户数量而强行提高客户评级。
- 不得把 AI 推测写成公开事实。

## SQL 与数据规范

### 应做

- 客户、线索、证据、标签、评分、联系人、反馈数据应分表或分结构保存。
- 原始采集证据应尽量只追加，不覆盖。
- 更新评分、标签、联系人推荐时，应保留规则版本、Prompt 版本或更新时间。
- SQL 查询必须明确字段，避免长期使用 `SELECT *`。
- 批量更新、删除、去重前必须先验证影响范围。
- 去重应综合来源 URL、机构、团队、标题、发布时间、证据摘要等特征。
- 存储手机号、邮箱、微信号等敏感字段时，必须加密、脱敏或加访问控制。
- 普通查询默认不得展示敏感联系方式明文。
- 导出含敏感联系方式的 Excel/CSV 时，必须校验访问权限，并记录操作人、时间、范围、字段和任务 ID。

### 禁做

- 不得直接覆盖原始采集内容。
- 不得无条件批量更新客户优先级。
- 不得用评分结果反向修改证据。
- 不得删除销售反馈历史。
- 不得将手机号、邮箱、微信号写入普通日志、错误堆栈或调试输出。
- 不得把未经公开来源确认的联系方式作为确定字段入库。

## 事务与一致性规则

### 应做

- 涉及多表写入时必须使用事务，例如：
  - 新线索 + 证据片段 + 标签
  - 客户评分 + 评分理由 + 评分版本
  - 销售反馈 + 客户状态更新
- 批量采集任务必须支持幂等执行，重复运行不应产生大量重复线索。
- 长任务必须记录任务状态、开始时间、结束时间、失败原因。
- 任务状态应区分：已采集、已识别、已评分、已生成联系人、已生成话术、已人工确认。

### 禁做

- 不得在任务失败后留下半条客户卡片却标记为完成。
- 不得把“话术已生成”误标为“客户已联系”。
- 不得因为部分来源失败而丢弃整批已成功采集的证据。
- 不得让同一条线索产生多个互相冲突的当前优先级。

## 日志规则

### 应做

- 日志应记录任务 ID、数据源、采集范围、成功数量、失败数量、跳过原因、耗时。
- 识别和评分日志应记录规则版本、Prompt 版本或模型配置版本。
- 外部网页、采购公告、论文、专利等来源应记录 URL 和抓取时间。
- 错误日志应包含阶段、来源、异常类型和可定位信息。

### 禁做

- 不得在日志中输出完整邮箱、手机号、微信号。
- 不得只记录“失败了”而没有来源、阶段和异常类型。
- 不得把大段网页正文、论文全文或公众号全文写入普通日志。
- 不得让日志成为新的非结构化数据存储。

## 接口兼容规则

### 应做

- 对外输出字段应兼容 `README.md` 中定义的 Excel 字段。
- 接口返回必须区分：原始线索、识别标签、评分结果、联系人推荐、话术建议、销售反馈。
- 新增字段时必须保持向后兼容。
- 接口变更必须说明新增字段、删除字段、字段含义变化、默认值和迁移影响。
- 评分等级保持稳定：`A+ / A / B / C / D`。

### 禁做

- 不得随意重命名核心字段，如 `评分`、`评分理由`、`信息来源URL`、`跟进状态`。
- 不得把单值字段改成数组而不处理兼容。
- 不得改变评分含义却不更新规则说明。
- 不得让导出脚本依赖临时字段。

## 话术生成规则

### 应做

- 话术必须从具体证据出发，例如论文样机、采购公告、实验装置、成果转化新闻、招聘机械设计岗等。
- 对评级为 `A+` 和 `A`，且涉及 `设计优化痛点` 或 `样件迭代` 的客户，邮件/微信正文中必须嵌入“免费图纸可制造性评审（DFM）”提议。
- 免费 DFM 必须绑定具体信号，例如图纸优化、结构件变形、装配干涉、样件迭代、实验装置加工、试制验证等。
- 对 `B` 级客户，如果无法引用具体需求信号，话术不得使用“免费 DFM”作为泛泛促销，应改用“行业案例参考”“相关实验装置案例同步”“后续有样件迭代时可交流”等低压维系方式。

### 禁做

- 不得把“免费 DFM”当成所有客户的统一营销口号。
- 不得在没有设计优化、样件迭代或加工痛点证据时强行使用 DFM 钩子。
- 不得夸大客户论文、专利、新闻中的真实需求。
- 不得生成会让客户感觉被监控、被过度解读或被冒犯的话术。

## 销售反馈与评分修正规则

### 应做

- 销售反馈必须回写，并至少支持：`已联系`、`未回复`、`有需求`、`已报价`、`已成交`、`暂不需要`、`已有固定供应商`、`自己买了设备`、`预算不够`、`只是理论研究无实物`、`对接人没找对`、`价格不合适`、`交期不匹配`。
- 评分规则修正必须由反馈数据触发，不能凭感觉调参。
- 当某类标签连续 `10` 次跟进均反馈 `无实物需求`、`只是理论研究无实物` 或等价负反馈时，该标签权重必须触发人工 review，并考虑降权。
- 每周或每个迭代周期内，必须选取至少 `3` 个“高评分但最终未成交”的案例进行假阳性复盘。
- 假阳性复盘必须判断问题来源：信号识别错误、评分权重偏差、联系人推荐错误、话术切入点错误、客户真实无需求、价格/交期/固定供应商等非模型因素。

### 禁做

- 不得因单个客户反馈就随意调整全局权重。
- 不得只看成交案例，不复盘高评分未成交案例。
- 不得把所有未成交都简单归因于销售执行问题。
- 不得在没有反馈样本支撑的情况下调整核心评分权重。

## 排错规则

### 应做

- 排错时先定位问题发生在哪一层。
- 对错误评分，应回溯区域、机构类型、学科方向、需求信号、痛点信号、近期紧迫信号和假阳性扣分。
- 对采集缺失，应检查数据源可访问性、关键词、时间范围、网页结构变化和反爬限制。
- 对联系人错误，应检查联系人身份、公开来源、证据片段和推荐理由。
- 对话术异常，应检查是否引用真实证据，是否夸大客户需求。

### 禁做

- 不得只调高或调低分数来掩盖识别错误。
- 不得跳过证据链直接修改客户结论。
- 不得把网页不可访问、来源失效和客户无需求混为一谈。
- 不得用个别案例直接推翻全局评分规则。

## 测试规则

### 应做

- 测试必须覆盖高潜样本：高校工科课题组、科研院所、教授创业团队、硬科技初创企业、成果转化团队。
- 测试必须覆盖低潜样本：纯理论、纯算法、纯软件、纯仿真、标准设备采购、大批量低价加工客户。
- 评分测试必须同时验证分数和评分理由。
- 联系人测试必须覆盖有公开联系人、无公开联系人、联系人不确定等场景。
- 导出测试必须验证 Excel/CSV 字段完整、敏感字段权限控制有效。
- Prompt 或评分规则变更后，必须跑固定回归样例集。

### 禁做

- 不得只测试关键词命中，不测试上下文含义。
- 不得只测成功路径，不测无联系人、无 URL、重复线索、来源失效。
- 不得只验证有输出，不验证输出是否可追溯、可解释、可交接。

## 文档规则

### 应做

- 文档必须说明每个 Agent 的职责边界、输入、输出、验收条件。
- 评分规则、标签规则、字段定义、导出格式、Prompt 版本管理规则必须单独记录。
- 业务规则变更时，应同步更新文档和测试样例。
- 文档必须明确：MVP 阶段只辅助客户经理判断，不自动触达客户。

### 禁做

- 不得写只有愿景、没有输入输出和边界的 Agent 文档。
- 不得让文档字段和实际导出字段长期不一致。
- 不得省略低优先级客户、假阳性规则和 AI 置信度兜底规则。
- 不得把未经验证的业务假设写成确定事实。
