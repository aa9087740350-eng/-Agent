# 通告驱动联系人补全子流程

本文档定义当输入只有一个通告、采购公告、成果新闻或项目通知时，如何从公开来源补全潜在用户联系人。该流程属于“公开线索采集层”和“联系人识别层”的交接子流程，由主控编排团队调度，联系人识别团队主责，数据契约与质量保障团队负责字段和敏感信息约束。

## 适用场景

- 用户提供一条采购公告、招标公告、学院通知、成果转化新闻或项目通告。
- 通告中只出现采购办、招标代理、学院办公室或项目联系人，但未明确真实技术需求方。
- 通告包含项目名称、设备/装置/夹具/试验台/样件等线索，需要查找可能的课题组、实验室或平台联系人。
- 已有线索评分较高，但联系人字段为 `未识别`、`未公开` 或 `待人工确认`。

## 不适用场景

- 用户要求根据姓名拼音、学校域名或常见邮箱格式猜邮箱。
- 用户要求抓取非公开通讯录、绕过登录权限或获取私人联系方式。
- 通告无 URL、无标题、无机构、无证据片段，且无法补充公开来源。
- 下游想把采购办公室联系人直接标记为真实技术需求方，但缺少公开证据。

## 输入要求

最小输入：

```text
通告标题
通告来源URL
采集日期
发布机构
证据片段
```

推荐补充输入：

```text
项目名称
采购品类或技术关键词
预算/项目编号
学院/实验室/平台名称
通告联系人及身份
附件标题或附件URL
```

缺少最小输入时，主控编排团队必须退回公开线索采集团队补齐；不能让联系人识别团队凭空搜索。

## 自动推进步骤

```text
通告输入
  -> 公开线索采集团队：提取通告事实和证据
  -> 需求信号识别团队：确认是否存在样件、装置、夹具、结构件、试制或设计优化信号
  -> 联系人识别团队：执行公开联系人补全
  -> 数据契约与质量保障团队：检查敏感字段、来源、状态和导出规则
  -> 客户卡片与话术团队：只使用已验证或待人工确认的联系人状态生成话术
```

如果通告已经有评分结果，主控编排团队可以从评分包直接进入联系人识别团队，但必须同时提供通告证据和来源 URL。

## 联系人补全检索顺序

联系人识别团队应按以下顺序检索和验证：

1. 通告正文和附件：识别采购联系人、技术联系人、项目负责人、学院/实验室名称。
2. 发布机构官网：查找同一项目、同一平台、同一实验室的公开负责人或平台管理员。
3. 学院/实验室/课题组主页：查找与项目关键词、设备用途、研究方向匹配的 PI、实验室工程师、项目助理或学生作者。
4. 导师主页和团队成员页：确认研究方向、实验平台、联系方式是否公开。
5. 论文、专利或成果新闻摘要：用项目关键词和团队名称交叉验证真实需求方，但不得把推测写成公开事实。
6. 学院科研秘书、公共平台负责人：当真实技术联系人未公开时，作为低优先级入口。

## 身份区分规则

| 类型 | 可作为推荐联系人 | 说明 |
| --- | --- | --- |
| 技术联系人 | 是 | 通告或公开页面明确负责技术参数、实验平台、项目执行或装置使用 |
| 课题组成员 | 是 | 与通告项目、设备用途或研究方向有公开证据关联 |
| 实验室工程师/平台管理员 | 是 | 常负责设备、装置、夹具、加工对接，回应概率通常较高 |
| PI/教授 | 是 | 适合建立信任，但冷启动回复率可能低 |
| 学院科研秘书/公共平台负责人 | 备选 | 适合作为进入学院或共享平台的入口 |
| 采购办公室联系人 | 有条件 | 只能标记为采购流程联系人，不得默认其为真实技术需求方 |
| 招标代理联系人 | 一般否 | 通常只负责招标流程，除非通告明确其可转接技术需求方 |

## 置信度与状态

联系人补全必须同时输出联系人匹配状态和联系方式状态：

| 字段 | 允许值 |
| --- | --- |
| 联系人匹配状态 | `公开确认` / `方向匹配待人工确认` / `仅通告流程联系人` / `未识别` |
| 联系方式状态 | `公开确认` / `未公开` / `待人工确认` |
| 联系方式展示状态 | `授权结果明文展示` / `脱敏展示` / `明文需权限` / `无联系方式` |
| 推荐置信度 | `高` / `中` / `低` |

置信度判断：

- 高：同一公开来源或多个公开来源同时确认联系人、身份、机构和联系方式。
- 中：联系人身份公开，研究方向或平台与通告高度匹配，但无法直接证明其负责该通告。
- 低：只能确认机构或学院入口，无法确认具体技术需求方。

## 输出字段

联系人补全包必须包含：

```text
线索ID
通告标题
通告来源URL
采集日期
发布机构
项目名称
通告联系人
通告联系人身份
通告联系人来源URL
推荐联系人
联系人身份
联系人匹配状态
联系方式
联系方式状态
联系方式展示状态
联系方式来源URL
推荐联系人理由
推荐置信度
证据片段
待人工确认事项
```

## 联系方式明细展示

客户经理人工复核结果中必须明确列出已公开确认的具体联系方式，并逐项说明来源。不得只写“有邮箱”“见官网”或只给联系人姓名。

联系方式明细列表必须使用以下结构：

```text
联系方式类型
联系方式值
联系方式状态
联系方式展示状态
联系方式来源URL
联系方式来源页面标题
联系方式证据片段
联系方式采集日期
公开位置说明
是否与推荐联系人同源确认
```

展示规则：

- `联系方式状态 = 公开确认` 且结果视图面向客户经理人工复核时，`联系方式值` 应具体展示，例如公开邮箱、公开办公电话、公开主页联系表单或公开平台页面。
- `联系方式状态 = 未公开` 时，`联系方式值` 必须写 `未公开`，不得猜测补齐。
- `联系方式状态 = 待人工确认` 时，`联系方式值` 必须写 `待人工确认`，并列出需要人工确认的原因。
- 同一联系人有多个公开联系方式时，应逐条列出，每条都必须有独立来源 URL 或明确同源说明。
- 若联系方式来自通告流程联系人而非推荐技术联系人，必须在 `公开位置说明` 中标明“通告流程联系人”，不得混同为技术需求方联系方式。

普通日志和非授权导出默认不得展示明文邮箱、手机号或微信号。需要导出明文联系方式时，必须由数据契约与质量保障团队检查权限和审计字段。

## 禁止事项

- 不得通过姓名拼音、学校域名、学院域名或常见邮箱格式猜测邮箱。
- 不得把招标代理或采购办公室联系人直接当作真实技术需求方。
- 不得为了补齐客户卡片虚构联系人身份、职务、联系方式或回应概率。
- 不得把“方向匹配待人工确认”写成“公开确认”。
- 不得展示没有来源 URL 或证据片段支撑的具体联系方式。
- 不得在普通日志中输出完整邮箱、手机号或微信号。
- 不得在无公开来源时把 AI 推测写成事实。

## 交接验收

| 来源团队 | 接收团队 | 交接物 | 验收条件 |
| --- | --- | --- | --- |
| 公开线索采集团队 | 联系人识别团队 | 通告事实包、来源 URL、采集日期、证据片段、附件线索 | 最小输入完整，通告联系人身份不被默认改写 |
| 需求信号识别团队 | 联系人识别团队 | 需求信号、痛点信号、近期紧迫信号、假阳性风险 | 有助于判断真实技术需求方，不包含最终评级 |
| 联系人识别团队 | 数据契约与质量保障团队 | 联系人补全包、联系方式状态、来源 URL、证据片段 | 未猜测联系方式，敏感字段有展示状态 |
| 联系人识别团队 | 客户卡片与话术团队 | 推荐联系人、身份、匹配状态、联系方式状态、推荐理由 | 话术可按联系人状态生成，不把待确认联系人写成事实 |

## 完成条件

- 至少尝试过通告、附件、发布机构官网、学院/实验室/课题组主页的公开验证路径。
- 每个推荐联系人都有来源 URL、证据片段和推荐理由。
- 联系方式未公开时明确标记，不使用猜测补齐。
- 通告流程联系人和真实技术需求方被清楚区分。
- 输出结果可直接进入客户卡片，但仍停留在客户经理人工确认边界。
