# 团队：`销售反馈优化团队`

### 使命

负责“销售反馈与模型优化层”，记录客户经理反馈，组织假阳性复盘，并用数据触发评分权重、标签规则和联系人/话术策略的 review。

### 负责内容

- 负责：跟进状态、未成交原因、反馈记录、假阳性复盘、权重 review 触发。
- 维护：反馈字段枚举、反馈写入规则、复盘模板、反馈到模型优化的证据链。
- 产出：反馈摘要、复盘报告、规则调整建议。
- 评审：反馈字段变更、状态流转变更、权重 review 建议。

### 工作边界

- 范围内：记录和分析销售反馈，提出有数据支撑的优化建议。
- 范围外：凭感觉修改评分权重、删除反馈历史、把话术生成标记为已联系。
- 可以修改：反馈字段文档、复盘模板、反馈分析报告。
- 未经批准不得修改：评分权重、识别 Prompt、话术 Prompt、原始线索证据。
- 共享 ownership：与动态评分排序团队共同评审权重调整；与需求信号识别团队共同复盘假阳性标签；与数据契约与质量保障团队共同维护反馈字段和事务一致性。
- 必须升级协调的情况：连续 `10` 次同类标签负反馈；每周高评分未成交复盘；反馈状态影响客户当前优先级。

### 启动读取

1. `README.md`：理解销售反馈字段和反馈闭环目标。
2. `AGENTS.md`：确认反馈必须回写，且不得因单个客户反馈调整全局权重。
3. `docs/agent-teams/scoring-prioritization-team.md`：确认评分团队如何接收 review 建议。
4. `docs/agent-teams/demand-signal-team.md`：确认假阳性复盘如何回到标签规则。
5. `docs/agent-teams/data-contract-quality-team.md`：确认反馈写入事务和字段兼容。
6. 缺失：反馈数据 schema、状态流转图、假阳性复盘模板、反馈分析脚本。

### 当前需求

- 需求：定义反馈团队，确保后续优化由反馈数据触发。
- 优先级：P1。
- 约束：不得只看成交案例；每周或每个迭代周期至少复盘 `3` 个高评分未成交案例。
- 已接受假设：当前项目尚无真实反馈数据，只建立章程和字段边界。
- 开放问题：反馈录入入口、权限、数据表和状态机尚未设计。

### 交付物

- 交付物：反馈记录、反馈摘要、假阳性复盘、规则 review 建议。
- 验收条件：反馈字段至少支持 README 和 AGENTS 中列出的状态；复盘能区分模型因素和非模型因素。
- 验证方式：检查反馈写入事务、历史保留、状态枚举、复盘样本数量和证据链。
- 截止时间或顺序依赖：客户经理人工触达后启动，周期性回传评分和识别团队。

### 协作接口

- 发送给：动态评分排序团队、需求信号识别团队、联系人识别团队、客户卡片与话术团队、数据契约与质量保障团队。
- 接收自：客户卡片与话术团队、客户经理。
- 交接物：跟进状态、未成交原因、成交状态、对接人是否正确、价格/交期/供应商等非模型因素。
- 验收条件：上游团队能判断问题来源是信号识别、评分权重、联系人推荐、话术切入点还是非模型因素。
- 冲突解决：单例反馈只记录不改全局；达到样本阈值后提交 review。

### 工作规则

- 启动后的第一步：确认反馈写入不会覆盖原始线索和历史反馈。
- 首选工具或命令：`rg` 查找反馈字段、状态和测试；未来多表写入必须使用事务。
- 必须运行的测试或检查：反馈写入、状态流转、历史保留、导出字段完整性。
- 安全限制：不得在普通日志、错误堆栈或调试输出中写明文联系方式。
- 文档要求：规则调整建议必须说明样本数量、负反馈类型、影响标签和建议 owner。

### 质量门槛

- 功能：反馈能驱动复盘，而不是替代证据链。
- 技术：反馈历史保留，多表写入事务一致。
- 文档：反馈枚举、复盘周期和 review 触发阈值明确。
- 交接：优化建议有样本证据，不直接改全局权重。
