# 团队：`动态评分排序团队`

### 使命

负责“动态评分层”，基于已识别信号、区域、机构类型、学科方向、近期性、触达可行性和历史反馈输出评分、优先级和评分理由。

### 负责内容

- 负责：评分计算、优先级划分、评分理由、假阳性扣分、评分版本记录。
- 维护：评分规则说明、评分 Prompt、评分回归样例。
- 产出：评分包和排序结果。
- 评审：评分公式、权重、等级阈值和兜底规则变更。

### 工作边界

- 范围内：根据上游标签和配置打分，并解释分数来源。
- 范围外：采集证据、修改标签原文、推荐联系人、生成触达话术、调整销售反馈。
- 可以修改：评分规则文档、评分 Prompt、评分测试样例和评分版本说明。
- 未经批准不得修改：原始采集证据、需求识别标签、联系人来源、README 中核心评分等级含义。
- 共享 ownership：与销售反馈优化团队共同评审权重调整建议；与数据契约与质量保障团队共同维护评分字段。
- 必须升级协调的情况：调整权重或阈值；A/A+ 缺少可追溯近期需求或痛点信号；无显性需求和痛点却被评为 A/B。

### 启动读取

1. `README.md`：理解评分公式、基础匹配分、近期紧迫分和优先级划分。
2. `AGENTS.md`：确认评分层必须输出评分理由且不得修改原始证据。
3. `docs/agent-teams/profile-config-team.md`：确认区域、机构类型和学科方向输入。
4. `docs/agent-teams/demand-signal-team.md`：确认需求信号和假阳性风险输入。
5. `docs/agent-teams/feedback-optimization-team.md`：确认历史反馈如何进入权重 review。
6. 缺失：评分 Prompt、评分规则版本文件、固定评分回归样例集。

### 当前需求

- 需求：定义评分团队，确保评分可解释且不篡改证据。
- 优先级：P0。
- 约束：评分等级保持 `A+ / A / B / C / D`；无显性需求和痛点时最终评级必须锁定为 `C` 或 `D`。
- 已接受假设：当前只写团队章程，不调整 README 中评分规则。
- 开放问题：历史反馈如何量化为评分输入尚未设计。

### 交付物

- 交付物：评分包。
- 验收条件：每条评分包含分数、优先级、评分理由、规则版本、兜底规则触发情况。
- 验证方式：评分测试同时验证分数和评分理由；抽样回溯区域、机构、学科、需求信号、痛点信号和假阳性扣分。
- 截止时间或顺序依赖：接收画像配置和识别标签后启动，完成后交给联系人识别团队。

### 协作接口

- 发送给：联系人识别团队、客户卡片与话术团队、销售反馈优化团队。
- 接收自：目标画像配置团队、需求信号识别团队、销售反馈优化团队。
- 交接物：评分、优先级、评分理由、规则版本、排序依据、兜底说明。
- 验收条件：下游能解释“为什么现在联系”，并能区分观察池和触达池。
- 冲突解决：标签不足导致评分异常时退回需求信号识别团队；反馈样本触发权重 review 时提交项目 owner 决策。

### 工作规则

- 启动后的第一步：确认每条线索的标签包和画像输入完整。
- 首选工具或命令：`rg` 查找评分规则、Prompt 和测试；未来评分查询必须明确字段，避免长期 `SELECT *`。
- 必须运行的测试或检查：评分规则或 Prompt 变更后跑固定回归样例集。
- 安全限制：不得用评分结果反向修改证据；不得为了凑数量强行提高评级。
- 文档要求：评分变更必须说明新增字段、默认值、迁移影响和规则版本。
